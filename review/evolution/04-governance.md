# 04 · 容量治理：记忆多了怎么办

记忆系统的失败模式不是"记不住"，是"记住了太多没用的，把有用的挤掉"。这一份只回答容量问题。

## 1. 四道闸

按顺序生效，前一道拦住了就不进下一道：

| # | 闸 | 作用对象 | 触发 | 动作 |
| --- | --- | --- | --- | --- |
| 1 | 写入配额 | 每层条数 | 新条目要写入时 | 先淘汰，仍满则拒绝并提示整理 |
| 2 | 注入分级 | 每层注入条数 | 每次会话首轮 | 只取 L0+L1；L2/L3 不进注入 |
| 3 | 时间衰减 | 每条分数 | 每次算 score | 分数随 `exp(-age/60)` 下降 |
| 4 | 整理合并 | 全库 | 每日 / 80% 配额 | dream 合并重复、拆分过长、归档低分 |

## 2. 注入分级

不是所有记忆都该进上下文。四档：

| 档 | 条件 | 进注入 | 条数上限 | token 上限 | 例子 |
| --- | --- | --- | --- | --- | --- |
| **L0 常驻** | `status=core` 或 `pinned=true` | 是 | 12 | 400 | 「不要自动 commit」 |
| **L1 排序** | `status=active` 且分数达标 | 是 | 层预算内 | 层预算 | 「这个仓库用 pnpm」 |
| **L2 按需** | `status=candidate` 或分数低 | 否 | — | 0 | 弱推断的偏好 |
| **L3 归档** | `status ∈ {archived, superseded}` | 否 | — | 0 | 过期的端口号 |

L2 不是"没用"，是"这次用不上"。模型可以主动 `memory_manager_search` 查到它；用户也能在 UI 看到。L3 默认连搜索都不返回（要 `all=true`）。

**为什么要有 L2**：一条"这个项目 2024 年用过 webpack"的记忆，对当前任务没用，但用户问"我们以前用什么打包"时有用。把全部候选塞进上下文是 token 浪费，全删掉是信息损失。L2 是中间态。

## 3. 预算：四层结构

"给多少 token"不是一个数字，是四层决定：总盘怎么算、层间怎么分、单位怎么卡、超了怎么截。

### 3.1 总盘：按上下文窗口动态算

```text
budget = clamp(contextWindow × 0.015, 800, 2400)   // 拿得到窗口
budget = 1600                                      // 拿不到，用默认
```

| 上下文 | 预算 | 能放条数（35 token/条） |
| --- | --- | --- |
| 32K | 800（下限） | 23 |
| 64K | 960 | 27 |
| 128K | 1920 | 40（条数上限先撞） |
| 200K | 2400（上限） | 40 |

1.5% 的依据：系统提示 + 工具表占 15–25%，对话历史 50–60%，输出预留 10–15%，记忆给 1.5–3% 是保守区间。

下限取 800 而不是 600：四层最低配额合计 500，600 只剩 100 给排序，等于没有排序空间。

`contextWindow` 从 `agent.model.current()` 取；取不到就用 1600。**不要**用"猜一个 32K"代替——猜小了会白白丢记忆，猜大了会撑上下文。

### 3.2 层间分配：min / max + flex

| 层 | min | max | 满配条数 |
| --- | --- | --- | --- |
| `global` | 100 | 300 | 8 |
| `workspace` | 200 | 650 | 16 |
| `scene` | 80 | 300 | 8 |
| `session` | 120 | 350 | 8 |
| 合计 | 500 | 1600 | 40 |

算法（flex 模型）：

```text
1. 每层先给 min，合计 500
2. 剩余 budget - 500 按优先级分配：session > workspace > scene > global
   每层最多拿到 max
3. 如果所有层都要超过 max，从 global 开始砍回 min
4. L0（core/pinned）优先占用所在层的额度，不跨层借
```

session 优先级最高的理由：一次对话的约束通常 2–5 条，但每条都直接改变下一步动作。额度小，价值密度最高。

total 只到 1600 是因为 max 之和就是 1600；上下文超过 128K 时多出来的预算放不进去，由 §3.3 的条数上限先撞线。

### 3.3 条数与门槛

| 约束 | 值 |
| --- | --- |
| 注入总条数 | ≤ 40 |
| L0 常驻 | ≤ 12 条（`core` / `pinned`） |
| L1 排序 | 余下 28 条 |
| L1 准入门槛 | `helpful > 0` 或 `confidence > 0.7` |
| 单条 token | ≤ 60（超了说明该做成 procedure） |

L1 门槛的作用：新学的条目 `helpful=0`，靠 confidence 进；弱推断（0.4）进不来。40 条不会变成 40 条噪音。

### 3.4 双单位卡口

token 估算有 ±20% 误差（不同 tokenizer 不同）。两道都卡：

```text
estTokens ≤ budget       软
bytes ≤ budget × 4       硬（1600 → 6400 字节）
```

取更严的那道。只卡 token 不卡字节，一条超长英文行会把单条预算吃穿（英文 4 bytes/token，中文 3 bytes/token，都按保守值算）。

### 3.5 用户记忆段与自动段的竞争

用户记忆段现有上限 **128 KiB 字节**，中文约 30–43K token——这个量级能撑爆 32K 上下文。但它是现有行为，改了就 breaking。

所以只加软约束（纯增量，不改现有渲染）：

| 用户段大小 | 自动段 | UI |
| --- | --- | --- |
| < 8K token（约 24 KiB） | 正常 | 无提示 |
| 8–24K token | 降到 min（500） | 「手写记忆较大，自动记忆已缩减」 |
| > 24K token | 0 | 「手写记忆占用过多上下文，建议精简」 |

用户段估算同样按 3 bytes/token（中文）与 4（英文）取更严。

这条不是"优化"，是兜底：没有它，两段各自合法、加起来爆上下文，用户只会看到模型开始忘事。

### 3.6 渲染顺序与截断

渲染从宽到窄：`global → _shared → workspace → scene → session`（先总则后特例），收尾声明写"越靠后越具体，冲突时后面的赢"。

截断规则：

- L0 不截断；超硬顶才报警，并只保留前 12 条
- L1 从 `global` 开始砍
- 块尾加一行 `… 12 more not shown; memory_manager_search to look up.`
- UI 显示 `本次注入 40/47 条 · 1.5k/1.6k token`

### 3.7 为什么不是越大越好

- 长注入块 → 模型对每条的平均注意力下降
- 低分条目混进来 → 错误注入率上升
- prefill 成本首轮线性增长

优化方向是信噪比，不是数量。推论：**L2 按需检索比 L1 全量注入更划算**——一条记忆 10 次会话用 1 次，注入 10 次浪费 9 次。这也是评分公式里 `helpful` 占 0.20 的原因。

### 3.8 默认值要在评测里定

不拍脑袋定 1600。A/B 四档：800 / 1200 / 1600 / 2000，看四个指标——重复提问率、纠正复发率、错误注入率、平均轮数。如果 1200 与 1600 效果差 < 5%，默认降到 1200。

见 `06-safety.md` §5.2。

## 4. 分数与衰减

```text
score = 0.45 * confidence
      + 0.25 * exp(-ageDays / 60)
      + 0.20 * log(1 + helpful) / log(1 + maxHelpful)
      + 0.10 * pinned
```

| 项 | 含义 | 为什么这个权重 |
| --- | --- | --- |
| `confidence` | 证据强度（由代码算，不信模型自报） | 最重；但不到 0.5，因为时间会改变事实 |
| `ageDays` | 最后更新时间 | 60 天半衰；三个月前的端口号本来就该降权 |
| `helpful` | 被注入后确实起作用的次数 | 归一化到当前库的最大值，避免绝对值膨胀 |
| `pinned` | 用户手动置顶 | 只占 0.1，不能靠置顶压过证据不足 |

`confidence` 的计算（`03-flows.md` §6 证据门的产物）：

```text
base = { user_explicit: 0.95, user_correction: 0.90, tool_verified: 0.80, model_inference: 0.40 }
confidence = clamp(base + 0.03 * (independentEvidence - 1) - 0.15 * contradictions, 0, 0.99)
```

`independentEvidence` 是**不同会话**的证据数（同一会话重复说不算）。`contradictions` 是冲突计数。

**为什么不让模型自报 confidence**：模型对"我有多确定"的估计没有校准。让它报，结果是全部 0.9——那就等于没有这个字段。代码用证据类型算，模型只负责提供证据。

## 5. 条数配额

| 层 | 软上限 | 硬上限 | 满了先淘汰 | 再满 |
| --- | --- | --- | --- | --- |
| `session` | 30 | 50 | 30 天未用的 candidate | 拒绝，提示"本会话已记满" |
| `scene` | 60 | 100 | archived → candidate | 拒绝，提示整理场景 |
| `workspace` | 120 | 200 | archived → candidate 低分 | 拒绝，提示整理 |
| `global` | 60 | 100 | archived → candidate 低分 | 拒绝，**必须用户处理** |
| 合计 | 270 | 450 | | |

**绝不静默丢高置信新条目**。配额满时宁可拒绝并告诉用户"记忆满了，去整理"，也不要偷偷删一条旧的高分记忆来腾位置——后者会让用户觉得"记忆会自己消失"。

## 6. 晋升阶梯

```text
episode（轮次摘要，不注入）
   │ 同一 key 在 ≥2 轮出现，或 user_explicit
   ▼
note（candidate，可注入但不主动）
   │ confidence ≥ 0.6，或 2 条独立证据
   ▼
memory（active，正常注入）
   │ helpful ≥ 3 且 harmful = 0，或用户置顶
   ▼
core（常驻，L0）
   │ 同 key 的 procedure 成功执行 ≥ 3 次
   ▼
playbook（带步骤的做法，注入只放标题）
   │ 用户确认
   ▼
skill（技能文件，写入 skills/）
```

| 跃迁 | 条件 | 谁触发 | 可撤销 |
| --- | --- | --- | --- |
| episode → note | 有证据 | 复习器 | 是（删条目） |
| note → memory | confidence ≥ 0.6 或 2 会话证据 | 复习器 / dream | 是（降级） |
| memory → core | helpful ≥ 3 且 harmful = 0 | dream | 是 |
| core → playbook | procedure 成功 ≥ 3 次 | dream | 是 |
| playbook → skill | **用户点确认** | 只有用户 | 是（删技能文件，有 `.bak`） |

**降级**：

| 条件 | 动作 |
| --- | --- |
| `harmful ≥ 2` | → `archived`（注入后被纠正两次，说明它有害） |
| 180 天未注入且未读 | → `archived` |
| 冲突 30 天未解决 | `active` → `candidate`（不删，但不能继续影响行为） |
| 所在工作区路径失效 90 天 | → `archived` |

## 7. 重复与合并

### 7.1 写入时的去重

身份 = `layer + workspace + key`。同 key 视为同一语义槽位：

- 新证据与旧条目**不矛盾** → 合并进同一条：`evidence` 追加，`boundary` 追加，`updated` 刷新。**不新建第二条**。
- 新证据与旧条目**矛盾** → 新条目 `active`，旧条目 `superseded`（保留文件，注入时不选）。
- 没有 key → 用归一化文本 + 字符二元组 Jaccard：

```text
Jaccard(a, b) ≥ 0.82  → 视为重复，合并
0.60 ≤ Jaccard < 0.82 → 标 related（UI 提示"可能重复"，不自动合并）
```

0.82 是保守值：宁可留两条相似记忆，也不要错误合并两条语义不同的（"用 pnpm"和"不要用 pnpm 的 lockfile"字面很像，语义相反）。

### 7.2 dream 的合并

dream 可以跨 key 合并，但必须满足：

- 同一层（不跨层合并）。
- 至少 2 条证据指向"这是同一件事"。
- 合并后条目的 `boundary` 必须是各条的并集，不能丢。
- 草案里给出 `merges[].reason` 和 `merges[].evidence`，用户能看到为什么。

**禁止整段重写**：合并只产出"新条目 + 旧条目 archived"，不修改旧条目的正文。旧文件留在 `.trash/<ts>/`，可整批回滚。

## 8. 冲突处理

| 冲突类型 | 判定 | 处理 |
| --- | --- | --- |
| 与用户记忆冲突 | 同 key 或 Jaccard ≥ 0.82，语义相反 | 自动条目进 `pending`，**不写入**；用户确认后才写 |
| 同 key 自动冲突 | 两条都 `origin=auto` | 新证据赢；旧的 `superseded` |
| 不同 key 但语义矛盾 | 例如「用 pnpm」vs「用 npm」 | 两条都保留，都标 `conflict`，UI 提示；dream 提议合并 |
| 事实过期 | `validTo` 已过 | 降 `candidate`，注入时不选 |

**用户记忆永远赢**，与层无关。但有一个例外：**事实类**且自动条目有更新的可复核证据（用户上个月手写"端口 3000"，本周工具实测 8080），不直接覆盖，进 `pending` 让用户确认。这样既不静默改用户的东西，也不让过期事实一直压着新证据。

**规则类**（偏好 / 纠正）没有这个例外：用户写的规则永远赢，自动条目只能提议。

## 9. 健康度面板

UI 的「记忆 → 自动记忆」顶部放一块：

```text
┌─────────────────────────────────────────────────────┐
│ 自动记忆   工作区 87 / 200   全局 34 / 100           │
│ 注入 8 条 / 1.1k token（上限 1.6k）                  │
│ 候选 12 · 冲突 2 · 待确认 3 · 过期 5 · 归档 21       │
│ [立即整理]  [查看待确认]  [导出]                     │
└─────────────────────────────────────────────────────┘
```

指标定义：

| 指标 | 计算 | 预警 |
| --- | --- | --- |
| 条数 | 各层 `status != archived` 的条数 | ≥ 80% 软上限变黄 |
| 注入 token | 上次注入的实际估算值 | ≥ 90% 预算变黄 |
| 候选数 | `status=candidate` | ≥ 30 提示"有 30 条弱记忆，可整理" |
| 冲突数 | `conflict=true` | ≥ 1 变黄 |
| 待确认 | `pending.json` 条目数 | ≥ 1 显示 badge |
| 过期 | `validTo` 已过或 TTL 已到 | ≥ 10 提示整理 |
| 归档 | `status=archived` | 只统计，不预警 |

**80% 触发提示，不是自动整理**。自动整理会在用户不知情时改动记忆，那是"自进化"最容易被讨厌的地方。提示 + 一键整理，主动权在用户。

## 10. 批量操作（UI）

| 操作 | 范围 | 确认 | 可撤销 |
| --- | --- | --- | --- |
| 停用 | 单条 / 多选 | 否 | 是 |
| 删除 | 单条 / 多选 | 是（写墓碑） | 30 天内可恢复 |
| 提升为用户记忆 | 单条 | 否 | 是（移回） |
| 限定到场景 | 单条 | 是 | 是 |
| 合并 | 2+ 条 | 是（预览合并结果） | 是（整批回滚） |
| 清空某层自动记忆 | 整层 | 是（二次确认） | 是（进回收站） |
| 重置学习（清墓碑） | 全库 | 是（二次确认 + 输入确认词） | 否 |

"重置学习"是唯一不可撤销的操作，所以要输入确认词，且明确写"清空后，你删过的记忆会被重新学到"。

## 11. 容量规划的依据

为什么是 200 条 / 1600 token 这个量级：

- **200 条 × 平均 30 token = 6000 token**。如果全注入，占 32K 上下文的 19%，太多。
- **只注入 L0+L1（≤30 条）**，约 900–1200 token，占 3–4%。这是可持续的比例。
- **200 条足够覆盖**：一个项目的约定（20 条）+ 个人偏好（30 条）+ 常用流程（20 条）+ 历史事实（50 条）+ 缓冲区（80 条）。
- 超过 200 条时，真正的问题不是"存不下"，是"检索不准"。这时候该做的是整理（合并同类），不是扩容。

这些数字都要在评测里验证（`06-safety.md` §4），不是拍完就定。
