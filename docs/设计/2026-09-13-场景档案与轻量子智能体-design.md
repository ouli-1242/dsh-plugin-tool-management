# 场景档案与轻量子智能体 设计

**Status:** approved

- **日期**：2026-09-13（批准同日）
- **命名裁定（用户）**：页面/用户可见名称统一为「**场景**」；目录 `~/.dsh/scene-memory/` **不改名**（里面仍是记忆，内部协议 `rules-*` 照旧）；人设目录为 `~/.dsh/subagents/`。
- **范围裁定（用户）**：场景 = 记忆 + MCP + Skills + **子智能体绑定**，一个版本交付；钩子不做；斜杠命令不做（与 skills 触发方向相反、无增量）；子智能体走**轻量人设**路线，不采用官方 agent-preset 插件组合（对"给主模型几个随叫随到的人设"过重）。
- **关联**：`docs/审查/2026-09-13-全项目对抗性审查.md`（本设计不含 index.ts 拆分，但新增代码按域模块落文件，不往 index.ts 堆）。

## 1. 术语

| 术语 | 含义 |
|---|---|
| 场景 | `~/.dsh/scene-memory/` 一级目录（现状不变），名即场景名 |
| 场景记忆 | 场景目录内的 `.md`，启用场景的正文注入系统提示词（现状不变） |
| 场景档案 | 场景的可选配置：MCP 工具启停集 + 技能启停集 + 子智能体绑定清单 |
| 当前模式 | 至多一个场景处于"当前模式"：其档案被应用到运行时；退出恢复切换前快照 |
| 人设（子智能体） | `~/.dsh/subagents/<name>.md`：frontmatter（可选）+ 正文 = 人设提示词 |
| 子智能体运行 | 主模型经 `subagent_run` 工具创建的一次性 agent，跑完即弃 |

## 2. A 部分：场景档案

### 2.1 数据模型（扩展 `~/.dsh/tool-management/rules-index.json`，仍是唯一侧车）

```jsonc
{
  "version": 1,
  "rules": { /* 现状不变 */ },
  "groups": { /* 现状不变 */ },
  "active": null,            // 记忆注入的启用场景集合（现状不变，多选语义）
  "mode": {                  // 新增：当前模式（只承载 tools/skills 两段的生效）
    "scene": null,           // 处于当前模式的场景名；null = 自由模式
    "snapshot": null         // 进入模式时的 { tools, skills } 运行时快照，退出时恢复
  },
  "archives": {              // 新增：每场景档案——三段**自由搭配**，均可独立缺省
    "<场景名>": {
      "tools": ["github/create_issue", "tavily/search"],   // 可选段：勾选的工具选集（key=<server>/<tool>）
      "skills": ["dsh/commit", "codex/review-pr"],         // 可选段：勾选的技能选集（key=<rootKey>/<name>）
      "subagents": ["code-review", "java-expert"]          // 可选段：绑定的人设名清单
    }
  }
}
```

**自由搭配原则（用户裁定）**：一个场景可以只选记忆（完全没有 `archives` 条目 = 现状行为），也可以任意组合记忆 + MCP / Skills / 子智能体。三段相互独立：
- **记忆**：跟随「启用场景」多选（现状机制）；
- **子智能体绑定**：也跟随「启用场景」多选并集（§3.3）——**不依赖当前模式**，所以"记忆 + 子智能体"型场景勾上即生效，无需进模式；
- **tools / skills 档案**：经「当前模式」生效（单选，避免多场景启停冲突）——只在场景**定义了该段**时才被应用。

**勾选集语义（用户裁定）**：段内存储的是「勾选的启用集合」。清单来自**实时发现**——只有当前实际存在的工具/技能/人设才会出现在勾选器里（已经有的才能勾），后安装的工具、新技能、新建人设自动出现在下次打开的勾选器中。应用时该域运行时启停**置为与勾选集完全一致**：勾 = 启用，未勾 = 停用；段未定义 = 该域完全不碰；段已定义但全不勾 = 合法（全部停用）。

### 2.2 切换语义（状态机）

- **进入模式 S**（显式用户动作，UI 按钮；仅当 S 的档案定义了 tools 或 skills 段才有意义）：① 快照当前 MCP 工具启停全集 + 技能启停全集 → `mode.snapshot`；② **只应用 S 档案中已定义的段**：把该域运行时启停置为与勾选集完全一致（勾选集中已不存在的条目跳过并列入结果里的失效清单，不算失败）；未定义的段保持运行时现状不动；③ 记忆启用集收窄为 `{S, _shared}`（用户之后仍可自由多选，不再受模式管）；④ 写 `mode = {scene: S, snapshot}`。全程走既有写锁串行。
- **退出模式**：恢复 `mode.snapshot`（未被动过的段恢复等于无变化）→ `mode = {scene: null, snapshot: null}`。记忆启用集与子智能体可用性**不**恢复（均跟随用户当前的启用选择）。
  - 实现口径（2026-09-13 修复批回填）：MCP 停用表**按快照原文整体回写**——模式自己写进去的键（未勾服务器的 `['*']`）必须随之消失，否则退出后用户环境仍被静默停用；「快照后新增键保持现状」的旧合并规则已废弃（它把模式写入的键一并留住）。技能只写快照列出的键（既有批量通道语义），模式期间新增的技能保持现状。模式期间的手动改动按「手动改动不自动回写档案」条不保留。
- **切换到另一模式 T**：先退出（恢复旧快照）再进入 T。
- **手动改动不自动回写档案**：进入模式后再手动启停工具/技能，只影响运行时；卡片上「保存到场景」按钮把当前运行时启停**重写**为该段的勾选集（显式动作，防静默覆盖）。
- **失败语义**：任一步应用失败（写 sidecar 失败等）→ 立即恢复快照并返回 `{ok:false}`（fail-closed，与修复后的 writeHistoryRetention 同哲学）。
- **子智能体绑定与模式无关**：见 §3.3——按「启用场景」并集实时生效，进不进模式都一样。

### 2.3 应用机制（全部复用既有写通道，零新机制）

- MCP 工具启停 → 既有 `mcpm-tool-enabled` 的底层写函数（disabledTools sidecar；**订正（2026-09-13）**：该通道实际是无 .bak 的 `writeJsonFile`，可逆性靠内存快照 + 先落盘的 `mode.snapshot`，原文此处曾称「自带 .bak」）；
- 技能启停 → 既有 skill enable/disable 批量通道（override provider 遮蔽，源文件不动）；
- 子智能体绑定 → 纯读取约束（见 §3.3），无运行时写。

### 2.4 UI（页面改名「场景记忆」→「场景」）

- 场景卡片三段：**记忆**（现状列表）/ **档案**（`+ 添加工具集 / 技能集`——弹出**实时发现清单的勾选器**：只有当前实际存在的条目才能勾，预勾当前启用状态方便微调；可整段移除；全不勾 = 合法即全部停用）/ **子智能体**（人设勾选器，同样只列已发现的人设，可全不选）。
- 卡片右上：`设为当前模式` / `退出模式`（互斥，至多一个场景在模式中，模式中卡片有常驻标记）；**只定义了记忆或记忆+子智能体的场景不显示模式按钮**（没有 tools/skills 段可应用）。
- `/scene-memory` 斜杠命令输出追加当前模式与档案摘要（命令名保留内部协议）。

## 3. B 部分：轻量子智能体

### 3.1 人设存储：`~/.dsh/subagents/<name>.md`（一个文件 = 一个人设，与场景记忆同哲学）

```markdown
---
description: 擅长 Java 后端实现与重构；需要写或改 Java 代码时调用   # 路由信号，缺省取正文首行
model: deepseek-v4-pro        # 可选；缺省继承主会话
tools: read, glob, grep       # 可选白名单；缺省不限制（用基础组合全集）
---
你是资深 Java 工程师。（正文 = 人设提示词，注入子代理 systemPrompt）
```

发现规则与场景记忆一致：两相扫描 + 指纹缓存；文件名 ≤64 字符、不含路径分隔符；**无 frontmatter 也能跑**。UI 上人设不入回收站（删了就是删了，v1 从简；文件操作走只读发现 + 手删）。

### 3.2 模型工具（2 个，工具总数 10 → 12）

- `subagent_list`：返回 `[{name, description, available}]`（available = 场景绑定校验结果）。
- `subagent_run{agent, task}`：**官方 `ctx.subagents` 薄封装**（Spike 后修订，不再直连 `agents.create`）：
  1. 读人设；**场景绑定校验**（§3.3）；
  2. `const run = await ctx.subagents.start({ provider: 'spawn', label: 人设名, parent: 调用 agent, signal: exec.signal, prompt: [text(task)], persona: 人设正文, toolFilter: 白名单 → { allow: [...] }, maxDepth: 1, agentOptions: { model? } })`——start() 即完成创建+投递（S1 官方解）；
  3. 结果 = 官方 `settleRun` / `finalAssistantOutput`（S2 官方解），截断 ≤16 KiB 返回；
  4. run 用后即弃（官方前台语义：collection 后 dispose；子会话不进 History）。
- **确认门**：`tools/pre-execute` 对 `subagent_run` 默认 `ask`（花真 token），设置 `requireConfirmForModelSubagentRun` 可关——与 rule_manager_write 同模式。
- **并发**：v1 串行队列（同一时刻至多 1 个子代理运行），后续再放开；`maxDepth: 1` 防递归套娃。
- **spawn provider 在场性**：运行时探测 `ctx.subagents` 是否已有 `spawn` provider；缺失则由本插件挂载 `@deepseek-ai/dsh-subagent-spawn-in-process`（peerDependency，`apply()` 注册），挂载声明进 cordis.patch.yml。
  - **实现偏离（2026-09-13 裁定，用户批准默认方案）**：落地为 `ctx.subagents.list()` 探测（官方通道）→ 已注册即跳过 → 缺失才经 `createRequire` + `apply(ctx, {providerName:'spawn'})` 挂载 → 失败把原因原样抛给模型；`cordis.patch.yml` **不**插入该包的挂载行，改为在文件内写明取舍注释。理由：① yml 的 `insert` 行是启动期解析，换台没有该包的宿主会因单行加载失败拖垮整棵插件树，而缺 provider 时受影响面只有一个 `subagent_run` 调用；② 该行与运行时兜底挂载存在双挂载窗口（同名 provider 重复注册）。`package.json` 以**可选** peerDependency（`peerDependenciesMeta.optional`）声明该包，宿主/profile 自带时仍可自行挂载。

### 3.3 场景绑定语义（与记忆「无配置全启用」同哲学）

`subagent_run` 执行时取**当前启用场景集合**的 `subagents` 清单并集：并集为空 → 所有人设可用；非空 → 仅清单内人设可用，越界直接返回结构化错误并列出可用名单（不 ask、不猜）。纯读取约束，零运行时写。

## 4. Spike 结论（2026-09-13 代码级验证完成，全部只读）

| # | 问题 | 结论 |
|---|---|---|
| S1 | 子代理任务投递入口 | **官方解**：`SubagentStartRequest.prompt: ContentBlock[]`，`ctx.subagents.start()` 即创建+投递，无需手动驱动 inbox |
| S2 | 完成等待与最终文本 | **官方解**：`settleRun` / `finalAssistantOutput`（dsh-subagent 导出）；`SubagentRun` 为受管一次性运行，前台用后即弃 |

| S4 | 子代理工具白名单 | **官方解**：spawn provider `capabilities = { agentOptions, outputSchema, depthLimit, toolFilter, persona: true }`，`toolFilter` 官方以 scoped `tools.restrict()` 实现（prompt 消失 + 执行拒绝） |

## 9. 非干扰原则（第一性原理，用户裁定为最高约束）

插件的一切行为必须是 DSH 原生能力的**附加层**，不得干扰原生的上下文注入、规则、会话流程。逐条对照：

| 触点 | 性质 | 保证 |
|---|---|---|
| `~/.dsh/scene-memory/`、`~/.dsh/subagents/`、`tool-management/` sidecar、插件 `data/` | 插件自有命名空间 | DSH 原生流程不读这些文件 |
| `SystemPrompt.section`（场景记忆/人设段） | 官方 API，自有段名 `tool-management:*`、order 3000（官方空档） | 只增不改：不碰 DSH 任何既有段；确定性文本满足前缀缓存契约 |
| `tools.register / guard / restrict` | 官方 API | 只增不改：新增工具与停用遮罩均为插件自有工具/自有 MCP 工具 |
| `ctx.subagents.start` | 官方 seam | 子代理经官方 provider 创建，不绕过 loop、不改代理循环 |
| `cordis.patch.yml` | 官方 patch 层 | 仅按官方机制替换两行并挂载自身；双挂载守卫防重复 |
| 场景档案应用 | 只写插件自有 sidecar（停用表/技能遮蔽状态） | 不触碰 DSH settings/会话/规则文件；快照/回滚保证可逆 |

**红线**：任何时候不得为插件功能修改 DSH 原生文件的语义、不得给原生段改名/改序、不得让插件的注入内容破坏前缀缓存契约。违反任何一条即为架构回归。

## 10. UI 重构 v2（用户裁定）

- TOOLS 顶栏七 tab（左→右）：**场景 / MCP / 技能 / 子智能体 / 提示词 / 记忆 / 会话**（AGENTS.md→提示词，History→会话）。
- 职责拆分：**场景页**管编排（场景建删、三段档案、当前模式）；**记忆页**管记忆内容 CRUD/回收站/预算；**子智能体页**管人设文件 CRUD（subagent-create/update/delete/get ops）。
- 档案 MCP 段两级：先勾**服务器**（清单=全部配置服务器，含未运行的，来自 mcpm-list），最右「选工具」进入该服务器工具明细钻取页。数据模型 `mcp: Record<server, '*' | string[]>`——`'*'` 整台（guard/restrict 原生支持通配，服务器后加载也被拦），数组=指定工具。
- 归一化：段键值为 null 视为**未定义**（客户端只发送已定义段；服务端双保险）。

## 11. 未采纳方案

- **官方 agent-preset 组合当子智能体载体**：preset 是插件组合目录、会话创建时加入，与"运行中即用即弃"不符且对轻量人设过重（用户裁定）；preset 留作将来"重型模板"的正统载体。
- **每人设注册独立工具**（`subagent_code_review` 等）：工具清单随文件增删抖动，tool list 不稳定；单工具 + list 更符合官方单工具 + 参数路由的形态（与 ZCode Agent 工具同构）。
- **用 `tools/restrict` 控制人设可见性**：单工具形态下无 per-persona 工具可 restrict；改为 execute 时校验（§3.3），语义等价且更简单。

## 12. v2.1 增量（2026-09-13 用户追加需求，同日实现 + 浏览器验证）

### 12.1 子智能体导入（`subagent-import`）

- 入口：子智能体页「导入」→ 弹窗（拖放或点选）→ `subagent-import`。
- 口径：一个 `.md` = 一个人设，**只看文件名**（zip 内的目录层级忽略）；接受 `.md` 与 `.zip`，可多选、可拖入。
- 重名**跳过并报告**（与技能导入同一策略，绝不覆盖既有文件）；非法名 / 空内容 / 超限条目单条跳过，其余照常导入（部分成功语义）。
- 限额：单文件 8 MiB、合计 32 MiB、单次 200 个文件、zip 条目 2000。

### 12.2 记忆导入（`rules-import`）

- 入口：记忆页「导入记忆」→ 弹窗含「导入到场景」字段（**默认留空 = 全局**）+ dropzone → `rules-import`。
- 口径：`.zip` 内带目录 → **目录路径即场景/分组**（`工作/standup.md` → 场景 `工作`，多级目录按分组路径落盘）；裸 `.md` → 落到弹窗所选场景（留空 = 全局）。
- **文件即真源**：导入即把 `.md` 原文写进 `<场景>/<名>.md`（不改写 frontmatter、不做派生），并登记索引（order/enabled/updatedAt）。
- 重名跳过并报告；`SKILL.md`（bundle 形态）本轮不支持 → 跳过并回报原因（避免把 bundle 拆成散文件）。
- 安全：绝对路径、`..` 穿越、隐藏项一律丢弃并回报。

### 12.3 全局记忆：不选场景 = 任何对话都注入

- **修复的缺口**：根层（`scene-memory/*.md`）记忆此前能被发现、能在「全局」卡片里管理，但 `resolveActiveScenes` 只启用「场景名 + `_shared`」，根层的空串从不入集合 → **永远不注入**（发现与注入两套口径不一致）。
- 现语义：根层 = 「全局」桶，**恒常启用**（与 `_shared` 同级、不受场景开关影响），任何对话都注入；场景与 `_shared` 语义不变。
- 连带修复三处（缺一不可）：① `resolveActiveScenes` 把 `''` 加入活动集合；② `rules-create` 此前用 `isValidGroupPath('')===false` 拒绝空场景、且用 `${group}/${name}` 拼 id（根层条目会变成 `/名字` 悬空 id）→ 改为允许空场景 + 与 `parseId` 同构的 id；③ 网页端新建按钮的 disabled 条件里硬要求场景非空 → 去掉该子条件。
- UI：场景字段提示「留空 = 全局（任何对话都注入）」；全局卡片加「任何对话都注入」标记；记忆场景选择器首项为「全局（不选场景 · 任何对话都注入）」。

### 12.4 文案收口

- 子智能体页介绍改一句话：「一个人设 = 一个 Markdown 文件（~/.dsh/subagents/），正文就是该子代理的系统提示词。」
- 人设「描述」字段提示改「一句话即可：模型据此判断何时调用它。」（字段本身是单行输入，未变）。

### 12.5 落点与复用

- 纯逻辑：`src/imports/upload.ts`（base64 解码 / ZIP 魔数识别与解包 / 路径校验 / 人设与记忆落点规划），单测 `test/import.test.mjs`（9 例）。

## 14. 第四段：bundle 导入 + never 审批预检（2026-09-13，同日实现 + 实测）

### 14.1 记忆导入支持 bundle 形态（修订 §12.2 的「本轮不支持」口径）

- 触发形态：zip 内 `<场景>/<名>/SKILL.md` → 该条按 **bundle** 落盘 `scene-memory/<场景>/<名>/SKILL.md`，**同层文件作附件**平铺进同一目录（附件的字节原文不改写）。
- 与 §12.2 的关系：§12.2 只定义 flat 落点；bundle 纳入同一条 `rules-import` 通道，落点与 `rules-create` 的 bundle 形态一致（正文 `SKILL.md` + 同层附件），不新增通道、不新增 op。
- 规划层之外**服务层复检一次**（防绕过规划层的调用方，与 `rules-attach` 同口径）：附件名非法 / 内容为空 / 单个超 8 MiB / 合计超 16 MiB → **逐条跳过并回报**，不阻断同批其余条目。
- 计数口径：UI「已导入 N 条记忆」按**记忆条数**计，bundle 算 1 条（附件不计条数）；`skipped` 名单里 bundle 内被跳过的条目以 `<名>/<附件名>` 形式列出。
- 拖放：记忆页与子智能体页共用同一 `ImportModal` 的 `dsm-dropzone`；本段完成**实拖**验证（证据见日志第四段）。

### 14.2 never 审批策略下的确认门口径（宿主端）

- 背景：DSH 审批策略是两层——会话 fold `approval/policy` 优先，其次插件 `config.policy`（默认 `ask`；见 `dsh-user-approval` 的 `effectivePolicy`）。「完全权限」预设（`dsh-permission-presets`：`sandbox=danger-full-access` + `approval=never`，自述 "without approval prompts"）**写的是会话级 fold**；该状态下一切 `ask` 在审批层被直接判 `rejected`（`decide()` 在派发 answerer 之前短路），确认卡不会弹出。
- **口径（2026-09-13 用户裁定，方案 B）：never = 用户在预设层面已预先批准一切确认门 → 三个走确认门的工具（`rule_manager_write` / `skill_manager_create` / `subagent_run`）在 never 会话里直接放行（`next()`），并写一条插件审计日志留痕（`confirm-bypass`）。**
  - 理由：① 预设的语义就是「不要再问我」；② 与 DSH 官方子代理工具一致——`dsh-tool-subagent`（`subagent` / `subagent_fork`）**没有 ask 门**，完全权限下照常运行，只有插件的 `subagent_run` 被自己的确认门挡住会显得自相矛盾；③ 把 ask 交给审批层只会得到误导性的「用户拒绝」。
  - **这是插件自定策略，与宿主 `decide()` 的 never=自动拒绝 相反**（有意为之）：插件确认门的语义是「问用户」，用户已在会话层面声明不必再问；宿主那条 fail-closed 针对的是「没人可问」。
- **读取链（关键约束）**：必须用 `ctx.get('approval')`，**不能**用 `ctx.approval`——本插件 `inject` 未声明 `approval`，cordis 上下文代理沿 fiber 链找不到 provider 时会抛 `cannot get property "approval" without inject`；旧实现把该异常吞在 `try/catch` 里，导致 never 探测恒为 `false`（2026-09-13 19:52 会话实测：模型只收到 `the user rejected tool "subagent_run"`）。`dsh-tools` 取同一条缝也是 `this.ctx.get("approval")`（其 `inject` 只有 `systemPrompt`）。
- 降级口径：探测只在读取链**完整可用**时生效；无 approval 服务、无 `exec.agent.session`、读取抛错一律返回 `false` —— 退回正常问询流程（ask），**绝不因为「读不到」而擅自放行**。
- 落地形态：探测抽到 `src/approval-policy.ts`（`isApprovalNever`），`src/index.ts` 的 `tools/pre-execute` 三个门共用一处前裁决；审计日志走 `src/skills/service.ts` 的 `pluginLog()`（全插件单一串行写队列，避免两处写同一文件交叉）；回归测试 `test/approval-policy.test.mjs` 用**真实 cordis Context + 真实 `ApprovalService`**、以**兄弟 fiber** 形态复现根因（服务建在 root 上会因 fiber 链可达而不复现，测试注释已标注该陷阱）。
- 演化记录：本口径先实现为「命中 never → `{kind:'deny'}` + 可行动报错」（同日实测通过），随后按用户裁定改为「命中 never → 放行 + 留痕」；拒绝分支只剩 `ask` 无 answerer 时由宿主 `dsh-tools` 给出的 `no approval channel is available`。
