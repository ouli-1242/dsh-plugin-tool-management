# 故障排查

按「症状」查。每条都给出**为什么**、**怎么确认**、**怎么修** —— 猜着改配置比不改更糟。

先记住四个入口，绝大多数问题在其中之一就能定位：

| 入口 | 看什么 |
| --- | --- |
| 设置 → 工具管理 → **兼容** | 宿主版本、本插件适配版本、可用能力数、降级项、更新状态；右上「复制诊断信息」 |
| `$DSH_HOME/tool-management/mount.json` | 这一轮插件**真的挂上过**吗、挂的是哪个版本、声明了哪些服务名 |
| `node scripts/doctor.mjs`（源码检出） | 模块身份、能力静态视图、裸模块契约、挂载心跳，一份完整报告 |
| `$DSH_HOME/tool-management/tool-management.log` | 插件自己的日志（滚动到 `.log.1`） |

`$DSH_HOME` 在 Windows 上默认是 `C:\Users\<你>\.dsh`，Linux / macOS 是 `~/.dsh`。下面统一写成 `<hub>` = `$DSH_HOME/tool-management`。

## 装完没有「工具管理」这一栏

**为什么。** 三种可能，且症状一模一样：

1. 装到了**另一个 profile**。`web` 与 `desktop` 是两个独立的插件目录，装 web 版不会让桌面版看见。
2. 宿主**没重启**。界面改动（前端资源）硬刷新就够，但插件本体是宿主进程加载的，必须重启进程。
3. 宿主**根本没加载这个插件**。最常见的原因是宿主升级后 `inject` 里的某个服务名改了 —— cordis 对未解析的 `inject` **不抛错、不打日志**，插件连 `apply` 都不会跑，界面上就是「连插件都不见了」。

**怎么确认。** 看 `<hub>/mount.json`：

- 文件不存在 → 插件从未挂载过，是第 3 种。
- 文件存在但 `iso` 是你上次重启**之前**的时间 → 这一轮没挂上，也是第 3 种。
- 文件里的 `pid` 已经不存在（进程早就结束了）→ 说明写它的那一轮宿主已经退出，之后重启过但没写新的，同样是第 3 种。

`mount.json` 里的 `injects` 就是这一轮插件声明要用的服务名清单。宿主升级后拿它和官方 release notes 对一遍，能直接看出是哪个服务名没了。

**怎么修。**

- 第 1 种：按端重装，`--profile web` / `--profile desktop` 别混。
- 第 2 种：web 版重启 `dsh web` 并硬刷新浏览器；桌面版**完全退出**应用再打开。
- 第 3 种：本插件无法自救 —— 它没被加载，代码一行都没跑。请把 `mount.json` 与官方日志一起提 issue，等一版适配。

## 装完是旧版

**为什么。** `@latest` 解析到的不一定是你以为的那一版：

- npm 镜像 / 代理有**同步延迟**，刚发布的版本可能还没到；
- pnpm 若开了 `minimumReleaseAge`（发布冷却），新版本在冷却期内会被跳过；
- 本地 npm 缓存里存着旧的 `@latest` 结果。

**怎么确认。** 兼容页的「本插件适配版本」是**这一轮实际加载的代码**里的版本号，不是 `package.json` 里写的。它和 `mount.json` 的 `version` 应当一致；两者都比 npm 上的最新版旧，就是装到了旧版。

**怎么修。**

```sh
# 指定确切版本，绕开 @latest 的解析
dsh plugin --profile web add dsh-plugin-tool-management@0.21.2
```

装完重启宿主，再看兼容页的版本号有没有变。pnpm 用户若确认是冷却期拦的，等过冷却期或显式放宽该策略；不要为了抢一个新版本关掉整个供应链防护。

## 出现两个「MCP」页签（或两套工具管理）

**为什么。** 同一份插件被加载了两次。常见于：先在某个位置装过、后来又装到 profile；或升级过程中旧目录没删干净，新旧两份同时在宿主可见的插件目录里。

**怎么确认。**

- `node scripts/doctor.mjs`：`module identity` 段里出现 `SEPARATE COPY` 的行，说明插件与宿主加载的是两份不同拷贝。
- `<hub>/mount.json` 的 `iso` 会**被后一次覆盖**，所以它只能告诉你「最近一次挂载」，不能用来数份数。
- 直接列宿主实际加载的插件目录，看有没有同名条目。

**怎么修。** 只保留一份：卸载后确认目录真的没了，再重装。

```sh
dsh plugin --profile web remove dsh-plugin-tool-management
# 确认 profile 的插件目录里已无残留，再装
dsh plugin --profile web add dsh-plugin-tool-management@latest
```

源码检出形态下，`node scripts/host-deps.mjs --fix` 会把插件依赖的官方包指到宿主那一份（junction），这解决的是**模块身份**问题，不解决「装了两份插件」的问题 —— 两者别混。

## 改完 MCP 配置后宿主起不来

**为什么。** 插件把 MCP 服务器写进宿主的 `cordis.patch.yml`。这个文件是宿主**加载插件**的入口，YAML 一旦不合法，宿主在加载阶段就失败 —— 表现是宿主起不来或起来后什么插件都没有，而不是「MCP 页签报错」。

**怎么确认。** 看 `$DSH_HOME/cordis.patch.yml` 的修改时间是否与你最后一次改 MCP 配置吻合；用任意 YAML 解析器试解析一次，报错位置就是问题所在。

**怎么修。** 每次改写前插件都会留一份备份，在 `<hub>/backups/`：

```
<hub>/backups/cordis.patch.yml[.global|.profile-<名字>].bak-<YYYYMMDD>-<HHMMSSmmmsss>
```

全局 patch 用 `.global` 标签，profile patch 用 `.profile-<名字>`；时间戳到毫秒并带三位进程内序号（共 12 位），按名字排序仍然等于按时间排序。

把最近一份**在出问题之前**的备份复制回 `$DSH_HOME/cordis.patch.yml`，宿主即可恢复启动。恢复后先只改一项、重启一次、确认没问题再继续 —— 一次性改很多项会让下次定位重新变成猜。

备份文件名带时间戳，按名字排序就是时间顺序。跨 profile 的备份会带 `profile-<名字>` 段，别拿错。

## 升级 DSH 后归档 / 删除 / 批量这些动作不能用了

**为什么。** 这些动作依赖宿主的**非公开成员**（工作区注册表、会话存储、投影缓存）。宿主换一代就可能改名、改形状。插件的原则是：**成员形状对不上就拒绝，绝不带着未知实现去改数据** —— 所以你会看到一条明确的拒绝，而不是数据被写坏。

**怎么确认。** 报错长这样：

```
宿主不支持该操作（delete）：<能力名> — <具体缺什么>。为避免用未知实现改动数据，操作在任何写入之前停止。
```

对照三处：

1. 兼容页的「可用能力」与降级项 —— 活宿主的实时判定；
2. `docs/COMPATIBILITY.md` —— 各宿主版本的能力矩阵（静态视图）；
3. `node scripts/doctor.mjs` —— 单机详细报告。

**怎么修。**

- 宿主版本**超出**插件的适配范围 → 升级插件到适配这一代宿主的版本。跨 minor 升级时旧适配会被主动拒绝安装，这是设计，不是故障。
- 宿主版本**在**范围内但能力探测失败 → 先把 `node scripts/doctor.mjs` 的输出提 issue。`SEPARATE COPY` 也会导致这一类失败，那种情况先按上一节修模块身份。
- 只是「读取类」能力缺失 → 对应页面会降级而不是拒绝，功能少一块但不会写坏数据。

## 安装时报 peer 依赖不符（ERESOLVE）

**为什么。** 本插件**只适配一代宿主**。当前版本按 DSH **0.2.1-rc.5** 的契约写（子智能体启动请求、身份比对、`connection.admit` 这几处都动过会静默改行为的语义），所以声明的范围只有这一代：

```
>=0.2.1-rc.5 <0.2.2
```

上界是**故意**的，下界也是：官方全程走 `x.y.z-rc.N` 预发布渠道，而 semver 有一条硬规则 —— **带预发布标签的版本，只有在比较器也带预发布标签、且 `[major,minor,patch]` 元组相同的时候才能匹配**。所以 `>=0.2.1-rc.5` 匹配不了 `0.2.2-rc.1`，范围只能逐段写；而写成多代并集（`0.1.7 || 0.2.0 || 0.2.1`）等于声明「这一版支持 0.1.7 起的每一代」，那是假的。

新 minor 已经动过若干会静默改行为的契约，旧适配继续跑在新宿主上，失败会以「功能莫名不工作」的形式出现，那时你无法判断是插件问题还是版本问题。**装上被拒 + 一版新适配，优于装上然后部分功能悄悄失效。**

还有一条**无法**用 range 消除的缺口：尚未枚举的新 rc 元组（比如 `0.2.2-rc.1`）在 npm 7+ 下会触发 ERESOLVE 告警。这不是写法问题 —— 不存在能匹配「任意未来预发布版本」的 range。

**怎么确认。** 报错里会带上本插件声明的范围和你当前的宿主版本。也可以先看兼容页的「当前宿主」：那里显示的是**实际跑着的**版本。

**怎么修。**

- 宿主比 `0.2.2` 新：等一版适配新宿主的插件。别急着用逃生门 —— 跨 minor 的契约变化正是这个范围要挡的东西。
- 宿主是 `0.2.0` 或更早：装**对应版本的插件**（旧插件带着旧范围，例如 0.16.x 那一代适配 `0.2.0-rc.2`）。升级宿主之后再升插件。
- 逃生门：确实需要强行安装时用 `--legacy-peer-deps`。它跳过的是**安装期检查**，不会让代码在宿主上变得兼容 —— 装完请务必看兼容页的降级项。

## 模型调不到某个工具

**为什么。** 工具可见性有四层，任何一层关着，模型就看不到：

1. **出厂默认**。二十条工具默认关闭（`*_list` / `*_save` / `*_remove` / `*_switch` 这类整域管理工具），因为它们要给**每个**模型请求都带上 schema，成本按 token 计；界面操作已经覆盖同样的事，模型只在确实需要时才值得开。
2. **停用表** `<hub>/mcp-disabled-tools.json` —— 全局关掉的工具。
3. **模型工具表** `<hub>/tool-table.json` —— 每一层（全局 / 会话 / 工作区）各有一份完整名单，全局那份只是新对话、新工作区的默认。
4. **当前作用域层**。按对话 / 按工作区模式下，这一层可能把工具关了，而全局是开的。

**怎么确认。** 界面上每个域与逐工具那一格都有徽章，按当前粒度现算。先确认徽章是「开」还是「关」，再看是哪一层关的 —— 工具表在每一层都是完整名单，所以「全局开着但这一层关着」是正常状态，不是 bug。

**怎么修。**

- 出厂默认关闭的：在模型工具表里显式打开一次，之后跟着层走。
- 停用表：MCP 页逐个打开。
- 作用域：切回全局层改，或在当前层单独改；行菜单「统一关闭」会立即停掉它，并把正在用它的会话 / 工作区的开关一并关掉（一次性动作，之后可重新打开）；页头「全部关闭」一次收掉这一域所有临时运行。

## 子智能体报 provider 不可用

**为什么。** 运行子智能体需要一个**运行器 provider**（进程内或子进程）。插件优先用宿主已注册的那个；宿主没注册时，会尝试自己挂载官方 provider 包。两条路都失败才会报错：

```
the <label> provider is unavailable: the host did not register it and mounting <pkg> from this plugin failed too (...)
```

**怎么确认。** 括号里是挂载失败的真实原因，先看它。常见的两种：宿主这一版没有这个包（`MODULE_NOT_FOUND`），或插件与宿主加载了两份不同拷贝导致注册对不上（`SEPARATE COPY`）。

**怎么修。**

- `SEPARATE COPY`：按「出现两个 MCP 页签」那一节修模块身份。
- 宿主确实没有这个包：改用宿主已注册的 provider（在子智能体页选可用的运行方式），或升级到带该包的宿主版本。
- 别用「手动往插件目录里塞一份 provider」来绕过 —— 那会造出第二份拷贝，把问题从「报错」变成「行为不一致」。

## MCP 工具全部被拒绝调用（停用表坏了）

**为什么。** 停用表是**安全边界**：它决定哪些 `mcp__*` 工具不许被调用。读不出来的时候，插件无法知道哪些本该被拦住，于是按 fail-closed 处理 —— 全部拒绝，而不是全部放行。

报错原文：

```
MCP 停用表损坏（<原因>）：所有 mcp__* 工具已被拒绝调用；请在 MCP 页重置停用表
MCP 停用表不可读（<原因>）：所有 mcp__* 工具已被拒绝调用；请检查文件权限或重置停用表
```

「损坏」是 JSON 解析不了，「不可读」是文件在但读不动（权限、被占用）。两者的处置不同。

**怎么确认。** 直接看 `<hub>/mcp-disabled-tools.json`：能不能解析、权限对不对。插件在覆盖写入前会强制留一份取证副本（复制失败就拒绝写入），所以原文件不会被悄悄盖掉。

**怎么修。**

- 不可读：先解决权限 / 占用，**不要**急着重置 —— 那份文件里是你所有的手工停用决定。
- 损坏：用 MCP 页的「重置停用表」。它会先取证再覆盖，重置后所有工具回到启用状态，你需要重新关一遍想关的。

## 更新检查显示「未知」或「已跳过」

**为什么。** 更新检查是**尽力而为**的，任何一种情况都会让它不工作，而它不会为此报错，也不会无限重试：

入口是面板右上角那颗**向上箭头的键**（作用域行右端）：点一下当场查（同一个 `update-status` op），不吃缓存。

| 显示 | 含义 |
| --- | --- |
| 检测到代理环境，已跳过更新检查（不穿透代理） | 环境里有代理配置。插件不穿透代理去连 registry —— 那会绕过你自己的网络策略 |
| 更新检查暂不可用 | 所有登记的源都不可达（首源 3 秒、回退源 4 秒）、离线，或返回内容解析不了。源顺序跟随宿主的插件源设置：配置的第一源 → fallback（默认含 npmmirror），并用宿主的双源测速决定先问哪个 |
| 取不到宿主版本，已跳过更新检查 | 宿主版本读不出来，无法判断哪个版本与你兼容 |
| registry 上没有与宿主 `<版本>` 兼容的版本 | 连上了，但没有任何一版适配你这一代宿主 |

**怎么确认。** 缓存文件是 `<hub>/update-check.json`，里面有上次结果与时间。它是纯缓存，删掉只会让下次重新查一遍。

**怎么修。** 大多数情况**不需要修** —— 它不影响插件任何功能。真要确认有没有新版，直接看 npm 上的版本列表，或手动指定版本安装。插件**从不自动更新**，也不会在后台下载任何东西。

## 侧车文件损坏了，怎么恢复

插件所有状态都在 `<hub>/` 下，都是可以单独删掉的 JSON 侧车。原则：**先备份再动手，一次只动一个文件**。

| 文件 | 坏了会怎样 | 怎么恢复 |
| --- | --- | --- |
| `mcp-disabled-tools.json` | 所有 `mcp__*` 被拒（见上一节） | MCP 页「重置停用表」 |
| `memories-index.json` | 记忆索引不可信 | 见下方「记忆索引隔离」 |
| `memories-index.json.quarantine.json` | 这是**隔离标记**，不是坏文件；有它 = 记忆写入被拒 | 场景页「一键修复」会自动清除（见下方「记忆索引隔离」） |
| `tool-table.json` | 模型工具表回落到默认名单 | 删掉，重启后在界面上重设 |
| `scope-overrides.json` | 会话 / 工作区覆盖写入失败；读侧回落到全局 | 作用域条出现「修复作用域文件」：确认后把损坏文件改名为 `.corrupt-<时间戳>` 留存，覆盖表按空表继续 |
| `scope-intent.json` | 全局意图写入失败；读侧等于「还没有意见」 | 同上；修复后下一次对账会从运行态反推意图 |
| `inject-settings.json` 等四个界面设置 | 该页设置回默认 | 删掉那一个，重启 |
| `mcp-settings.json` / `mcp-notes.json` / `mcp-known-tools.json` | MCP 页配置 / 备注 / 已知工具清单丢失 | 删掉对应那一个，重启后重设 |
| `subagents-index.json` / `skills-state.json` | 启停状态回默认（**正文文件不动**） | 删掉，重新启停 |
| `update-check.json` | 只是缓存 | 随便删 |
| `audit.jsonl` | 审计记录（追加写，不参与判定） | 可删；删了就少一段历史 |

**作用域侧车修复。** 作用域条上的写入错误旁边有「修复作用域文件」。第一次点击只切到「确认隔离…」，第二次才执行；它只改名、不覆盖，健康的文件什么都不做。隔离后 `scope-overrides.json` 的会话覆盖与 `scope-intent.json` 的全局意图回到默认（后者由下一次对账从运行态反推），原文件保留在 hub 里供排查。修复按钮只在有写入错误时出现，不影响正常设置。

**两个宿主同时写 hub。** web 与 desktop 共用同一个 hub 时，写入会通过 `.write.lock` 排队。看到「另一个 DSH 进程正在写同一个数据目录，等待超时」说明另一个宿主正卡在一次长写入：等它结束再重试即可。崩溃进程留下的锁最多挡一分钟，之后会被自动清理。

**记忆索引隔离。** 记忆索引读不出来时，插件不会静默重建（那会把你的启停 / 顺序 / 场景记录全丢掉），而是把原文件改名留存为 `memories-index.json.corrupt-<时间戳>`、写一个 `memories-index.json.quarantine.json` 标记，并**在重启后继续拦着**——没有这个持久标记，重启即失去闸门，第一次普通写入就会把空索引落盘。

看到标记说明：

1. 原文件已被改名留存（若改名失败，标记里记的就是原路径，没有留存副本）；
2. 正文 `.md` 文件一个都没动，场景 / 档案 / 记忆条目都还在那份留存文件里；
3. 在你处理之前，**记忆域的所有写入都被拒**。

**怎么修。** 场景页会出现一条横幅「记忆索引已被隔离，记忆写入全部被拒」，旁边一颗「**一键修复**」。它把留存文件装回 `memories-index.json`，修好后横幅消失、写入保护解除，并告诉你恢复了多少个场景、多少条记忆。

装回去之后仍然解析不了的话，它会**什么都不做**并保留现场 —— 修不了还硬写，等于把「一个已知的坏状态」换成「一个悄悄通过校验的空状态」。那种情况需要手工编辑那份 `.corrupt-*` 文件。

修好后 `.corrupt-*` **不会自动删除**：它是这次事故唯一的现场副本。确认一切正常后再手工清理。

**通用做法。** 不确定是哪个文件的问题时：先把整个 `<hub>/` 复制一份出来，再按「一次一个文件」试。`<hub>/memories/`、`<hub>/subagents/`、`<hub>/prompts/`、`<hub>/skills/` 里是你的**正文**，任何情况下都不要为了修侧车去删它们。
