# 架构

三张图。看懂它们就能回答「这条内容从哪来、为什么这个对话看得见、改完落到哪个文件」这三个问题。

细节不在这里 —— 代码注释里逐条记着每个决定的原因。

---

## 一、注入链路：内容怎么到模型眼前

插件的六个域（场景 / 记忆 / MCP / 技能 / 子智能体 / 提示词）各自算出一段文本，在**每一步请求开始前**塞进本轮消息。这条通道是宿主官方自己也在用的那一条，任何预设都关不掉它。

```
你的文件（真源）
  hub/memories/<场景>/*.md        记忆正文
  hub/subagents/*.md              人设
  hub/skills/**/SKILL.md          技能
  hub/prompts/*/AGENTS.md         提示词预设
  宿主服务里的 MCP 清单            服务器与工具
  hub/*.json                      启停 / 顺序 / 备注
        │
        │  每个域各自算一段文本（各域自带缓存，这一步不读盘）
        ▼
六个域：scene / memory / mcp / skills / subagents / prompt
        │
        │  宿主 agent/pre-step 瀑布，每一步请求前触发
        ▼
一条合成的 user 消息（每域一条，框架包住整段正文）
        │
        │  与会话表面上该域最近一条己方消息逐字节比对
        ▼
   一样          → 不发（零 token）
   不一样        → 追加一条新消息
   被压缩移出表面 → 比对不到 → 自动重发
   曾经注入过、现在空了 → 发一条「已清空」
        │
        ▼
模型上下文
```

三个后果值得记住：

- **每个域一条消息，不是一大坨快照。** 只改一个域就只重发那一条，轨迹里也各自一行、各显各的名字。
- **注入失败绝不影响这一轮对话。** 任何异常都在监听器里吞掉、原样放行 —— 宁可少一段提示，不能让对话中断。
- **子会话默认不收人设目录。** 人设的 `catalogDepth` 决定它在哪一层深度出现（默认只在顶层），这是减少噪声，不是禁止嵌套委派。

`AGENTS.md` 是**另一条**路：提示词域把它写进 `$DSH_HOME/AGENTS.md`（全局基线），由宿主自己的 `dsh-agent-instructions` 每步读取注入。所以「应用了预设但模型没反应」要分两种查：写没写进去（文件内容），和宿主有没有重读（宿主的刷新契约）。

## 二、四层作用域：同一个开关为什么在两个对话里不一样

按对话 / 按工作区模式下，一个会话看到的**每一格**取值都由四层叠加决定，自上而下，先有话说者赢：

```
   ① 会话覆盖   scope[domain][key]
      这个对话里显式拨过的开关 —— 永远赢
            │ 没这一格
            ▼
   ② 场景层     处于场景模式时（scope.scene 存在）
      按场景档案实时算：档案里有这一段 → 勾了开、没勾关
      档案里没这一段 → 这一层没话说
            │ 没这一格
            ▼
   ③ 基线       仅当 scope.detached === true
      会话创建时的冻结快照 —— 退出场景落回这里
            │ 没这一格
            ▼
   ④ 全局       实时值
      前三层都没话说时才轮到它
```

几条容易踩的边界：

- **退出场景落回基线，不是落回全局。** 全局是会变的；落回全局等于「退出场景时顺手把别人的改动也吃了」。
- **三态存储、二态展示。** 存储上是「没这一格 / 显式开 / 显式关」；界面上只有绿与灰 —— 停在某一层时看到的就是**这个对话的生效值**。
- **点回「跟随」会自动清掉覆盖。** 写侧判一次（新值 == 下层此刻的值就删键），读侧再判一次（下层后来被改成同一个值，那条覆盖就不该再起作用）。
- **记忆不收场景层。** 记忆的「在哪一层」由场景名 + 逐条开关决定，档案的记忆段已废弃；场景层只影响开关类域。
- **拿不到会话身份时一律按全局。** 冷恢复的临时 agent、宿主契约变更 —— 猜错的代价是「A 的设置漏进 B」，按全局最多是「这一处没隔离」，用户看得见且不串内容。
- **子代理与侧聊向上找父会话的作用域。** 否则父会话里藏起来的服务器 / 技能 / 工具表，派一个子代理就能重新看见。

工作区档的作用域键由**根会话的 cwd** 派生（会话头里没有 workspaceId），与下拉分组、工作区挂回同一口径。

## 三、写盘落点：每个改动落在哪个文件

插件产生的一切都在 `$DSH_HOME/tool-management/` 一个目录里，方便整体备份。

```
$DSH_HOME/
├─ AGENTS.md                    ← 宿主每轮读取的全局基线（插件按场景/预设写它）
├─ cordis.patch.yml             ← 宿主加载插件的配置入口（插件写 MCP 服务器时改它）
└─ tool-management/             ← hub：插件的全部状态
   ├─ memories/<场景>/<名>.md           记忆正文（真源）
   ├─ subagents/<人设>.md               子智能体人设
   ├─ prompts/<预设 id>/AGENTS.md       提示词预设库
   ├─ skills/                           插件新建 / 导入的技能（可写根）
   │
   ├─ memories-index.json               记忆启停/顺序 + 场景记录/档案/模式
   ├─ subagents-index.json              人设启停集合
   ├─ skills-state.json                 技能启停 / 首选 / 自定义目录
   ├─ scope-overrides.json              会话 / 工作区的四层覆盖
   ├─ scope-intent.json                 全局意图开关
   ├─ tool-table.json                   模型工具表（每层一份整名单）
   ├─ mcp-disabled-tools.json           全局停用表（安全边界，fail-closed）
   ├─ mcp-known-tools.json              见过的工具清单
   ├─ mcp-notes.json / mcp-settings.json / mcp-export.json
   ├─ inject-settings.json / scene-settings.json
   ├─ slash-settings.json / sidebar-settings.json
   ├─ trash-retention.json              回收站保留期
   ├─ update-check.json                 更新检查缓存（纯缓存，可删）
   ├─ mount.json                        挂载心跳：这一轮插件真的挂上了吗
   ├─ .write.lock                       跨进程写锁（临时；崩溃后最多挡 1 分钟）
   ├─ audit.jsonl                       审计记录（追加写，不参与任何判定）
   ├─ tool-management.log (+ .1)        插件日志（滚动）
   │
   ├─ backups/cordis.patch.yml[.global|.profile-<名字>].bak-<YYYYMMDD>-<HHMMSSmmmsss>
   │                                            改宿主 patch 前的备份（按层级各留 5 份）
   └─ trash/
      ├─ skills-trash/<id>/            六类回收站：条目 = manifest.json + 负载
      ├─ subagents-trash/<id>/         移入 = 移动（原位置立刻消失）
      ├─ prompts-trash/<id>/           绝不覆盖（恢复时目标已存在就报错）
      ├─ scenes-trash/<id>/            失败要回滚（搬了一半就搬回去）
      ├─ quick-prompts-trash/<id>/
      └─ memories-trash/<id>/
```

几条纪律：

- **正文与索引分开。** 索引坏了最多丢「启停 / 顺序 / 场景档案」，`memories/` `subagents/` `prompts/` `skills/` 里的正文一个都不会动 —— 所以任何修复都不要碰这四个目录。
- **写侧车一律原子写。** 半截文件比没有文件更糟：读不出来时多数路径会 fail-closed（停用表坏了就全部拒绝），而不是猜一个默认值。
- **安全边界上的文件有取证副本。** 停用表损坏时覆盖前强制留一份，复制失败就拒绝写入。
- **旧布局只搬不删、绝不覆盖。** 升级时的目录改名是幂等的一次性动作，搬不动的留在原地下次再试 —— 失败也绝不阻断启动。
